# 后端踩坑记录

修改 backend/ 下的代码时必读。

### 1. dev.command 中 .env 解析失败（2026-03-28）

**现象**：`TUSHARE_TOKEN 未设置`，但 `.env` 文件里明明有值。

**原因**：原写法 `source <(grep -v '^#' .env | sed 's/^/export /')` 没有过滤空行，空行变成 `export `（单独的 export 关键字），导致 bash 报错并中断 source，后续变量全部未设置。

**修复**：用 `set -a` 自动 export，同时过滤注释和空行。

**教训**：shell 脚本里解析 .env 文件，必须同时过滤注释行和空行。

### 2. dev.command 过重导致双击卡死 Finder（2026-03-28）

**教训**：双击运行的 `.command` 脚本必须极简极快。所有验证检查应该是独立脚本，不要塞进启动流程。

### 3. iCloud Drive 中双击 .command 导致 Finder 卡死（2026-03-28）

**教训**：项目在 iCloud Drive 时，永远不要用 `.command` 扩展名。用 `.sh` + 终端手动运行。

### 5. 修改代码后必须自验（2026-03-29）

**规则**：修改后端 Python → 需要重启后端：`bash stop.sh && bash dev.sh`。不能改完代码就说"你试试"，应该主动帮用户确认。

### 8. H1/H2 必须在支撑位附近才开始数（2026-03-29）

**正确逻辑**：
1. 先找支撑位（swing low 聚类，价差 < 3% 的归为一组，至少被测试 2 次）
2. 价格触碰支撑后，才开始计数
3. H1 = 触碰支撑后第一个 swing high
4. 回落不破支撑 → 下一个 swing high = H2
5. 跌破支撑 → 计数作废

**教训**：交易信号检测必须先确定市场结构（支撑/阻力），再在关键位置数形态。

### 9. H1/H2 是反包K线，不是 swing high（2026-03-29）

**正确定义**：
- 反包（bullish reversal bar）：跌完后，第一根阳线吞没前面阴线（close > 前阴线 high）
- H1 = 靠近支撑位，跌完后第一个反包
- H1 后又跌，等第二个反包 = H2
- 每个 H 之前必须先有一段下跌（至少 1 根阴线），不能连续计数

**教训**：交易术语"数H1H2"指的是数**反包K线**，不是数**波峰/swing high**。

### 12. 牛股集中营过滤条件过严导致常态性空数据（2026-03-29）

**教训**：多层 AND 过滤极易导致空集。每增加一层过滤前，先估算通过率。宁可多选入再靠排序分优先级，也不要过滤到空。

### 17. API 响应漏掉已计算的字段（2026-03-29）

**现象**：前端 `patternData.resistances` 始终为 `undefined`，压力位红圈画不出来。

**原因**：`server.py` 的 `/api/stock/{code}/patterns` 端点在构建 `json_response` 时，逐个 `.get()` 字段，手动写了其他字段但**漏掉了 `resistances`**。

**教训**：当后端函数返回的 dict 需要透传到 API 响应时，要么直接 `return signal_results`（不要手动逐字段复制），要么在逐字段构建后，**对照源函数的 return 语句逐行核对**，确保没有遗漏。
